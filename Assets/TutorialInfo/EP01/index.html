GAME ENGINEERING DETECTIVE · CASE 001

两万个箱子，真的要逐个移动吗？

《Factorio》式传送带优化的关键，不是把两万次移动做得更快，而是识别哪些相对关系根本没有发生变化。

畅通阶段：不需要。32 段传送带烘焙成一条运输线，每条车道每 Tick 只更新一个 Offset。

01
THE FIRST SUSPECT

传统方案：每个箱子保存绝对位置

从出口向入口遍历。前方有空间就推进；被挡住，就停在前一个箱子后面。直观、准确，但工作量会随物料数量线性增长。

NAIVE / O(N)

逐件推进

20,000 件物料意味着每个 Tick 至少访问 20,000 个位置值。

cost ≈ items × ticks
TRANSPORT LINE / O(1)*

整线位移

物料保存相对距离。畅通时相对关系不变，只需推进每条车道的 Offset。

absolute = relative + offset
02
BAKE THE ROUTE

32 段外观，1 条逻辑运输线

Unity 场景里的直线段和弯道只是作者工具。运行前，拓扑构建器按网格连接顺序烘焙成连续逻辑距离，并拆成两条车道。

01 / AUTHOR

场景传送段

32 个 BeltAuthoring，保存输入方向、输出网格和形状。

02 / BAKE

拓扑诊断

发现重复格、断链、孤岛与闭环，得到有序段列表。

03 / DOMAIN

1 Line · 2 Lanes

世界坐标退出模拟层，只留下整数逻辑距离。

04 / PRESENT

按需采样

生成快照时才把逻辑距离映射回直线与弯道的世界姿态。

03
THE DECISIVE LINE

核心差别，就在这个分支

头部还能完整前进时，Gap 后端不碰任何物料记录；每条车道只增加一次 Offset。只有抵达末端或发生堵塞，才进入压缩循环。

05
SAME WORLD, SAME RESULT

优化不能改变模拟结果

两套后端共享 Scenario、Topology、Snapshot 与状态哈希。模拟层是纯 C#：没有 GameObject、Transform、Rigidbody，也不依赖渲染帧率。

DETERMINISM CHECK

每一步，都能对账

Naive 与 Gap 在每个 Tick 都按相同字段计算 FNV-1a 状态哈希。只要任意箱子的 ID、类型、车道或绝对距离不同，哈希就会分叉。

hash_naive == hash_gap ✓
06
SIMULATION ≠ RENDERING

后台算两万件，画面只画 128 件

这是刻意分离，而不是偷换概念。逻辑物料全部参与模拟；表现层均匀抽样代表箱，再通过 RenderMeshInstanced 批量绘制。

128 / 20,000

约每 156 件逻辑物料取一个可见代表。快照展开、世界坐标采样、矩阵构建与绘制都计入“表现耗时”，不会混进模拟耗时。

07
WHERE THE TRICK ENDS

优化不是魔法：堵塞会让成本回来

闸门关闭后，出口物料先停下，间隙从前向后缩小。压缩边界扫过的物料必须被重新计算，因此 Gap 后端也会从 O(1) 逐渐回到 O(n)。

!

准确结论：只跳过没有变化的相对关系

不是“两万个物品永远只算一次”，而是当大量物料保持同样的相对排列时，没有必要反复更新每一个绝对位置。

CASE CONCLUSION
真正的优化，不是更快地移动两万个物品。
而是先找到那些根本不用计算的变化。
